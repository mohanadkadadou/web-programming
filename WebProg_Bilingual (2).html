What is an API?

API = Application Programming Interface — a contract for how software components communicate. Like a restaurant menu: you order → kitchen prepares → waiter delivers.

  • Web APIs: services accessed over HTTP
  • Examples: Google Maps API, Stripe, OpenAI
  • REST = Representational State Transfer
ما هي الـ API؟

API = واجهة برمجة التطبيقات — عقد لكيفية تواصل مكونات البرمجيات. مثل قائمة المطعم: تطلب → المطبخ يحضر → النادل يوصل.

  • Web APIs: خدمات عبر HTTP
  • أمثلة: Google Maps, Stripe, OpenAI
  • REST = نقل الحالة التمثيلية

✅ Pydantic Validation with Field()
from pydantic import BaseModel, Field, model_validator class BookCreate(BaseModel): title: str = Field(min_length=1, max_length=200) author_id: int = Field(gt=0) # greater than 0 isbn: str = Field(pattern=r"^\d{10}(\d{3})?$") # 10 or 13 digits price: float = Field(gt=0) # must be positive stock: int = Field(ge=0) # >= 0 # FastAPI auto-validates → invalid data returns 422 Unprocessable Entity # No manual validation code needed!
Field() Constraints
  • gt=0 — greater than 0
  • ge=0 — greater than or equal
  • lt=, le= — less than, less than/equal
  • min_length, max_length — string length
  • pattern= — regex validation
قيود Field()
  • gt=0 — أكبر من صفر
  • ge=0 — أكبر من أو يساوي
  • lt=, le= — أصغر من أو يساوي
  • min_length, max_length — طول النص
  • pattern= — تحقق regex
📦 Schema Separation (MUST KNOW!)
Why 3+ schemas?
  • BookCreate: what client sends to create
  • BookUpdate: all fields Optional (partial update)
  • BookResponse: what client receives (has id, timestamps)
  • DB Model: internal (may have password_hash!)

Security! Never expose internal fields. One model = disaster.

لماذا ٣+ schemas؟
  • BookCreate: ما يرسله العميل لإنشاء سجل
  • BookUpdate: كل الحقول اختيارية
  • BookResponse: ما يستلمه العميل (يحتوي id)
  • DB Model: داخلي (قد يحتوي password_hash!)

أمان! لا تكشف الحقول الداخلية أبداً.

📅 Week 10
Authentication: bcrypt, JWT & OAuth 2.0
المصادقة: bcrypt وJWT وOAuth 2.0
AuthN vs AuthZ
  • Authentication (AuthN): WHO are you? → Login/password
  • Authorization (AuthZ): WHAT can you do? → Permissions
  • You need AuthN BEFORE AuthZ
  • Golden rule: NEVER store passwords in plain text!
المصادقة vs التفويض
  • Authentication (AuthN): من أنت؟ → تسجيل الدخول
  • Authorization (AuthZ): ماذا يمكنك فعله؟ → الصلاحيات
  • تحتاج AuthN قبل AuthZ
  • قاعدة ذهبية: لا تحفظ كلمات المرور نصاً أبداً!
🔑 Password Hashing with bcrypt
How bcrypt works
  1. User enters password
  2. Server generates random salt
  3. Hashes: bcrypt(password + salt)
  4. Stores hash + salt — NOT original
  5. On login: rehash and compare hashes

Why bcrypt? Slow by design (defeats brute force). Includes salt automatically.

كيف يعمل bcrypt
  1. المستخدم يدخل كلمة المرور
  2. الخادم يولّد salt عشوائياً
  3. يُشفّر: bcrypt(كلمة المرور + salt)
  4. يحفظ hash + salt — وليس الأصلية
  5. عند الدخول: يعيد التشفير ويقارن

لماذا bcrypt؟ بطيء عمداً (يهزم brute force). يشمل salt تلقائياً.

# FastAPI + bcrypt import bcrypt # Registration hashed = bcrypt.hashpw( user.password.encode(), bcrypt.gensalt() ) # Login verification is_valid = bcrypt.checkpw( entered_password.encode(), stored_hash )
🎫 JWT — JSON Web Tokens (Structure!)
📌
JWT structure: header.payload.signature — three parts separated by dots
هيكل JWT: header.payload.signature — ثلاثة أجزاء مفصولة بنقاط
Header
{ "alg": "HS256", "typ": "JWT" }

Algorithm + type

الخوارزمية والنوع

Payload
{ "user_id": 123, "exp": 1680123456 }

Data + expiry

البيانات + انتهاء الصلاحية

Signature
HMAC-SHA256( header + payload, SECRET_KEY )

Prevents tampering

يمنع التلاعب

JWT Flow
  1. Client POSTs email/password to /auth/login
  2. Server verifies bcrypt hash
  3. Server creates JWT with user_id + expiry
  4. Server signs JWT with SECRET_KEY
  5. Client stores JWT (localStorage or cookie)
  6. Client sends: Authorization: Bearer TOKEN
  7. Server validates signature → extracts user_id

Key: Server doesn't store tokens — validates via signature alone!

تدفق JWT
  1. العميل يرسل email/password إلى /auth/login
  2. الخادم يتحقق من bcrypt hash
  3. الخادم يصنع JWT مع user_id + انتهاء الصلاحية
  4. الخادم يوقّع JWT بالـ SECRET_KEY
  5. العميل يخزن JWT
  6. العميل يرسل: Authorization: Bearer TOKEN
  7. الخادم يتحقق من التوقيع → يستخرج user_id
